## Problem

Reviewing the phase-1 list item by item, item #2 is auth. The sign-up side already has real decisions
behind it. The login/session side, what happens on every visit after the first one, had never actually
been decided, it only became visible as a gap once password made "which credential logs me in" a real
question instead of a rhetorical one.

## Sign-up methods, already decided (DEC-011, DEC-012, DEC-026)

Social login via Kakao, Apple, or Google, plus a phone number, always required regardless of which
provider a user signs up with (DEC-011). A provider-verified phone, Kakao in Korea specifically, can
satisfy the phone requirement directly without a separate OTP step. Otherwise standard OTP, or Korea's
carrier-based PASS verification for Korean numbers specifically (DEC-026), checked against the phone
number's own carrier country code, not the blended legal-country value DEC-012 uses elsewhere for the age
gate. A Korea-based user without a Korean phone number gets a redacted-ID fallback instead, government-
issued photo ID, self-redacted, reviewed by a trained human reviewer, no facial recognition or biometrics,
following Bumble's actual Korea flow (`internationalization-korea-2026-08-26.md`).

## Optional password, already resolved (`onboarding-flow-2026-08-26.md`)

Additive to social and phone, never a replacement for either. Lives in profile settings, not the
account-creation sequence, with periodic reminder notifications while unset. Reverses DEC-011's original
"password deferred" provision, filed as its own proposal already awaiting merger.

## Returning-user login, RESOLVED 2026-08-26: any valid credential logs the user into their one account

Phone number is the account's anchor identifier, it's mandatory and verified for every account regardless
of signup provider. Any of the following, presented at the same signed-out Get Started screen the entry
point already uses, logs the user into that one account: Kakao, Apple, or Google; phone OTP; or username-
or-email plus password, if a password has been set. No need to remember which method was used at signup,
whichever credential the user presents resolves to the same account.

**Biometric quick-unlock, RESOLVED 2026-08-26 (confirmed by Elvis).** Face ID, Touch ID, or Android
biometric equivalent gates access to an already-active session, the same pattern Instagram uses, not a
new server-side credential. Biometrics confirm the device owner locally via the native OS API, they don't
independently authenticate against WePop.

## Persistent session, RESOLVED 2026-08-26 (confirmed by Elvis): always active, not just "no periodic re-login"

Once logged in, the session stays active continuously, including while the app is closed or backgrounded,
the same pattern Instagram uses. It ends only on an explicit logout action or app deletion, nothing else
ends it. This matches industry standard for consumer social apps closely (Instagram, TikTok, Twitter/X all
work this way), a long-lived refresh token stored securely on-device (Keychain on iOS, Keystore on
Android), with no forced periodic re-login. Two additions on top of what Elvis described, not deviations
from it, see Deepak flags below: an explicit first-launch check to prevent a reinstalled app from silently
resuming an old session (iOS Keychain data can survive deletion, unlike Android Keystore), and a
server-side revocation capability kept in reserve (log out of all devices, forced logout on password
change or suspicious activity), invisible to the normal user-facing behavior described here.

## Account linking across providers, RESOLVED 2026-08-26 (revised from this file's earlier auto-link
resolution): verified-phone login plus explicit opt-in consent, not silent auto-link

Elvis's revised call: no silent auto-linking, follow industry standard instead. The actual industry
pattern (Auth0, Okta, and how Slack, Discord, and Notion each handle a matching-identifier collision) is
not a dead-end "go log in yourself" redirect either, both the blunter auto-link and my own original
recommendation were off. If someone attempts to sign up with a second provider (Google, say) using a phone
number already registered under a first provider (Kakao, say), the second provider's signup still has to
complete phone verification, OTP or a provider-verified phone, exactly as it would for any signup. Since
that verification is itself proof of phone ownership, and phone is the account's anchor identifier, the
system logs the user straight into their existing account rather than creating a duplicate or bouncing
them to a separate login screen. It then explicitly asks: "This phone number is linked to an account
signed in with Kakao. Add Google as another way to sign in?" Nothing is linked without that explicit yes,
declining still leaves the user logged into their real account, just without Google added as a future
credential.

## Account recovery, RESOLVED 2026-08-26 (reconciled 2026-08-27 against DEC-011): phone first, email
magic-link where set, customer service as the last resort

Primary path: phone OTP login is always available and self-serve, since phone is mandatory and verified
for every account regardless of signup provider, losing access to a social provider is never a lockout by
itself. **Reconciliation note, 2026-08-27:** DEC-011's original text named email magic-link or an emailed
code as the recovery channel, reasoning that email is collected from every account. That assumption no
longer holds, email moved to optional and out of onboarding entirely this session
(`onboarding-flow-2026-08-26.md`, "Profile completion"). Phone OTP is the channel that's actually
universal now, since phone stays mandatory regardless of signup provider, so it takes over as the primary
recovery path. Email magic-link stays available as a second option for any user who has set one in
profile settings, DEC-011's mechanism isn't wrong, just no longer the only or the default path. Fallback,
when the phone number itself is also lost or changed and no email is on file: the user contacts WePop
customer service. That support-side workflow (identity re-verification, how a request is queued and
actioned) isn't designed here, see "Not yet decided."

## Flags for Deepak, implementation, not decided here

- Persistent session needs a secure, long-lived refresh token (Keychain on iOS, Keystore on Android),
  surviving app restarts and device reboots, cleared only on an explicit logout action or app deletion,
  not on any timer.
- iOS-specific: Keychain data can survive an app deletion and reinstall, unlike Android Keystore, which is
  cleared on uninstall. Needs an explicit first-launch-after-install check (for example, a UserDefaults
  flag, which does get cleared on uninstall) that wipes any leftover Keychain session entry, otherwise
  "delete the app" would not reliably end the session on iOS the way it does on Android.
- Recommend a server-side session-revocation capability alongside the client-side persistent session: log
  out of all devices, and forced logout on password change or suspicious activity. Invisible to the
  user-facing behavior Elvis described, an operational safety net, not a change to it.
- Phone number is the durable account-linking key. A new-provider signup attempt must complete phone
  verification (OTP or a provider-verified phone) before the system checks for an existing match, ordering
  matters here, the phone-ownership proof has to come first.
- Account linking is consent-based, not automatic: a verified-phone match on a new provider logs the user
  into their existing account (the OTP or provider verification just completed doubles as the login step),
  then shows an explicit opt-in prompt before persisting the new provider as an added credential. Declining
  still leaves the user logged into their real account.
- The signed-out Get Started screen needs to support every login entry point at once: social buttons,
  phone OTP, username-or-email plus password when set, and a biometric prompt when a valid session already
  exists locally on the device.
- Biometric quick-unlock is a client-side feature gating access to an existing session via the native OS
  biometric API, not a new identity-verification flow against the backend.
- Account recovery via customer service needs its own workflow, not designed here, may reasonably reuse
  the Admin Portal pattern already in place for the Give Feedback table
  (`internationalization-korea-2026-08-26.md`), not confirmed.
